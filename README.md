## 1. Архитектура

```text
Запрос руководителя в интерфейсе/чате
             │
             ▼
Оркестратор: проверяет права, фиксирует период и запускает отчёт
             │
       ┌─────┴─────────┐
       ▼               ▼
CRM-коннектор       Коннектор телефонии
amoCRM API v4       API/экспорт провайдера
сделки + задачи     метаданные + аудио/ссылка
       │               │
       │          безопасное хранилище аудио
       │               ▼
       │       ASR: распознавание речи
       │       Анализ звонков: критерии качества,
       │       возражения, договорённости, следующий шаг
       └───────┬───────┘
               ▼
Нормализация и связывание по ID сделки/контакта,
ответственному и времени; контроль полноты и дублей
               ▼
Расчёт метрик + аналитический LLM-компонент
(LLM объясняет наблюдения только по переданным данным)
               ▼
Проверки: ссылки на исходные сделки/задачи/звонки,
неопределённость, отсутствие данных, аномалии
               ▼
Черновик отчёта руководителю → подтверждение человеком
```

**Компоненты и данные.** Оркестратор принимает запрос, ограничивает его периодом и проверяет роль пользователя. Коннектор amoCRM читает `/api/v4/leads` и `/api/v4/tasks` с пагинацией; телефония подключается через документированный API конкретного провайдера (провайдер в условии не назван, поэтому endpoint здесь не предполагается). Записи получают через разрешённый API/ссылку провайдера, распознают в текст ASR-моделью, затем извлекают факты по заданным критериям. До анализа звонок связывается со сделкой по идентификатору, а при отсутствии ID — по проверяемым метаданным; сомнительные совпадения помечаются, а не присоединяются автоматически.

Результаты промежуточной обработки и итоговый отчёт хранятся в защищённой БД с разграничением доступа и сроком хранения по политике компании. Аудио и транскрипты — отдельно, с минимально необходимым сроком хранения; в аналитическую модель передаются только нужные поля. Токены API хранятся в секрет-хранилище, а действия и доступы журналируются. При недоступности источника система явно показывает неполноту данных, а не строит видимость полного анализа.

## 2. Автоматизация, человек и риски

**Система делает сама:** собирает разрешённые данные за выбранный период; проверяет полноту; считает согласованные показатели (воронка, скорость обработки, просроченные задачи, конверсия, распределение по менеджерам); транскрибирует звонки; формирует ссылки на первичные источники и черновик отчёта. LLM может обобщать подтверждённые факты, но не должен самостоятельно объявлять причину провала сделки или оценивать сотрудника без проверяемых оснований.

**Человеку передаются:** подтверждение управленческих выводов и оценок качества; разбор неоднозначно распознанных или сопоставленных звонков; решения по персональным данным, спорным кейсам и любым действиям, меняющим CRM. Система по умолчанию работает только на чтение и не меняет сделки, задачи и записи звонков.

**Три ключевых риска/ограничения:**
1. **Неполные/несвязанные данные** (запись не привязана к сделке, задачи ведутся вне CRM). Снижение риска: сверка покрытия по источникам, явные статусы «нет данных», ручная проверка сомнительных связей.
2. **Ошибки ASR и выводов модели** (шум, акценты, галлюцинации или ложная причинность). Снижение риска: показывать фрагмент транскрипта и источник рядом с выводом, порог уверенности, выборочная проверка человеком; выводы без подтверждения не выдавать как факты.
3. **Персональные данные и доступ к звонкам.** Снижение риска: минимизация данных, RBAC, шифрование, аудит доступа, сроки удаления и согласование обработки с ответственными за безопасность/комплаенс. Юридические требования уточняются для конкретной юрисдикции и договоров.

## 3. Фрагмент Python для amoCRM

Пример находит сделки, созданные за последние 30 дней, у которых нет ни одной привязанной задачи, либо есть просроченная незавершённая задача. Он читает все страницы задач аккаунта, чтобы не принять старую привязанную задачу за отсутствие задач. Для крупного аккаунта в промышленной версии следует сузить выборку штатными фильтрами API, учитывать лимиты/429 и использовать инкрементальную синхронизацию.

```python
import os, time, requests
BASE = os.environ["AMO_BASE_URL"].rstrip("/")
HEADERS = {"Authorization": f"Bearer {os.environ['AMO_TOKEN']}"}

def pages(path, params=None):
    url = f"{BASE}/api/v4/{path}"
    while url:
        r = requests.get(url, headers=HEADERS, params=params, timeout=30)
        r.raise_for_status()
        data = r.json()
        yield from data.get("_embedded", {}).get(path, [])
        url = data.get("_links", {}).get("next", {}).get("href")
        params = None

def find_followups(now=None):
    now = int(time.time()) if now is None else now
    leads = list(pages("leads", {"filter[created_at][from]": now-30*86400, "limit": 250}))
    linked = {x["id"]: [] for x in leads}
    for task in pages("tasks", {"limit": 250}):
        lid = task.get("entity_id")
        if task.get("entity_type") == "leads" and lid in linked:
            linked[lid].append(task)
    return [{"id": x["id"], "name": x.get("name"),
             "reason": "no tasks" if not linked[x["id"]] else "overdue task",
             "overdue_task_ids": [t["id"] for t in linked[x["id"]]
                 if not t.get("is_completed") and t.get("complete_till", now) < now]}
            for x in leads if not linked[x["id"]] or any(
                not t.get("is_completed") and t.get("complete_till", now) < now
                for t in linked[x["id"]])]

if __name__ == "__main__":
    for deal in find_followups():
        print(deal)
```

Перед запуском: `AMO_BASE_URL=https://<адрес_аккаунта>.amocrm.ru`, `AMO_TOKEN=<OAuth access token>`; установить `requests`. В примере токен не зашит в код.
